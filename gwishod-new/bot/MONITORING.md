# Мониторинг доступности серверов из РФ

Модуль следит за тем, доходит ли трафик до наших VPN-узлов **из России**, и
пишет админам в Telegram, когда узел пропадает или возвращается. Проверки
идут через собственный [GEOPinger API](https://github.com/qqallvlx/geopinger-api),
поднятый на отдельной VPS.

## Главная идея

Узел может перестать работать по двум разным причинам, и реагировать на них
надо по-разному:

| Что видим | Что это значит |
|---|---|
| Не отвечает из РФ, **отвечает** из-за рубежа | заблокирован в РФ |
| Не отвечает ни из РФ, ни из-за рубежа | лёг сам сервер |
| Отвечает из части регионов РФ | блокировка началась у отдельных операторов |

Поэтому цикл двухступенчатый:

1. Проверяем адрес с точек **внутри РФ**. Всё в порядке — на этом всё,
   второй запрос не тратим.
2. Только если из РФ не ответила **ни одна** точка — делаем контрольную
   проверку с точек за пределами РФ (Казахстан, Бразилия, Индия, ЮАР).

Так на обычном обходе расходуется один запрос на сервер, а не два.

## Что и как проверяется

| Протокол | Адрес | Метод |
|---|---|---|
| IKEv2 | `ipAddress` из панели | TCP 22 |
| AmneziaWG | `ip_address` из панели | TCP 22 |
| VLESS | домен из `server_ip` | TCP 22 |

Везде один метод — TCP-порт 22. IKEv2 (UDP 500/4500) и AmneziaWG (UDP)
снаружи не пощупать: у UDP нет рукопожатия, «нет ответа» и «дошло, но
молчит» выглядят одинаково. Поэтому о доступности узла судим по
управляющему TCP-порту — если до него трафик из РФ не доходит, значит не
доходит и до сервера.

Порты задаются в `.env` отдельно для каждого протокола
(`MONITOR_IKEV2_PORTS`, `MONITOR_AWG_PORTS`, `MONITOR_VLESS_PORTS`), если
однажды понадобится проверять что-то ещё. Отдельным флагом
`MONITOR_VLESS_USE_CONFIG_PORT=1` можно добавить к проверке VLESS рабочий
порт из настроек сервера (8443 и подобные) — по умолчанию выключено.

Адреса берутся из основного API на каждом обходе, поэтому новые серверы
появляются в мониторинге сами, а удалённые исчезают. Выключенные в панели
серверы по умолчанию не проверяются (`MONITOR_INCLUDE_DISABLED=0`).

## Защита от ложных тревог

Это самое важное: ночной алерт из-за подвисшей точки проверки хуже, чем
алерт с задержкой в пять минут.

- **Инцидент открывается только после двух подряд неудачных обходов**
  (`MONITOR_FAIL_STREAK=2`), то есть примерно через 10 минут. Единичный
  сетевой миг игнорируется.
- **Сервер считается доступным, если отвечает хотя бы половина точек РФ**
  (`MONITOR_OK_RATIO=0.5`). Ниже порога — «частичная недоступность».
- **Если пингер сам недоступен, вердикта нет.** Проверки помечаются как
  «нет данных», счётчики не двигаются, алерты о блокировках не уходят.
  Вместо этого один раз приходит сообщение, что пингер молчит.
- **Массовое падение сводится в одно сообщение.** Если разом отвалилось три
  и больше узлов, и это половина всего списка, приходит одно сводное
  сообщение вместо десятков — так обычно выглядит проблема на нашей стороне,
  а не блокировка.
- **Дублей нет.** По одному инциденту уходит один алерт. Повторно бот
  напишет только если характер проблемы изменился (частичная недоступность
  переросла в блокировку) или через 6 часов как напоминание.

## Что приходит админам

**Когда узел пропал:**

```
🛑 Сервер недоступен из РФ
━━━━━━━━━━━━━━━
⚡ VLESS · 🇳🇱 GWAPP NL01
🌐 gwapp-nl01.freenets.store · TCP 22
🕒 08.08 в 21:35 (МСК)

Из РФ: 0 из 6.
Не отвечает: Москва, Санкт-Петербург, Екатеринбург, Новосибирск, Казань, Владивосток.
Из-за рубежа: 4 из 4, 38 мс.

Сервер живой, но из России до него не доходят — похоже на блокировку.
Продолжаем проверять каждые 5 минут — о восстановлении сообщим.
```

**Когда вернулся:**

```
🟢 Сервер снова доступен из РФ
━━━━━━━━━━━━━━━
⚡ VLESS · 🇳🇱 GWAPP NL01
🕒 08.08 в 22:10 (МСК)
⏳ Не работал 35 мин (с 08.08 в 21:35)
📉 Причина по нашим замерам: блокировка в РФ

Сейчас из РФ: 6 из 6, 41 мс.
```

**Суточная сводка** — каждый день в 23:50 МСК. Если всё было ровно, так и
написано: «Аномалий за сутки нет». Если были события — перечислены с
временем, длительностью и характером, отдельно показано, что не работает
прямо сейчас.

## Раздел в боте

Главное меню → **📡 Доступность из РФ**:

- **🗺 Состояние серверов** — все адреса со значком и доступностью из РФ;
  нажатие на проблемный открывает карточку с разбивкой по городам.
- **📉 События за сутки** — открытые и закрытые инциденты.
- **🔄 Проверить сейчас** — внеплановый обход, не дожидаясь расписания.
- **📋 Сводка за сегодня** — та же суточная сводка по требованию.
- **🔇 Приглушить уведомления** — на 1/4/8/24 часа. Проверки продолжаются и
  события пишутся в сводку, просто без сообщений. Удобно на время работ.
- **🩺 Проверить пингер** — живость сервиса, принят ли ключ, в каких странах
  есть точки, тестовый пинг. Первое, что стоит нажать после настройки.

## Настройка

Модуль включается одной строкой в `bot/.env` — без `GEOPINGER_URL` он
просто не запускается, остальной бот работает как обычно.

```ini
GEOPINGER_URL=http://57.129.126.169:8080
GEOPINGER_API_KEY=ваш_ключ_из_/opt/geopinger-api/.env
```

Остальные параметры (интервал, число точек, пороги, время сводки, порты)
описаны с комментариями в [`.env.example`](.env.example). Значения по
умолчанию рабочие, менять не обязательно.

После правки `.env` перезапустите бота.

## Стоимость обхода

Один обход = один запрос к пингеру на сервер (плюс второй только для
упавших). Проверка занимает 3–10 секунд, параллельно идёт 3 штуки
(`GEOPINGER_CONCURRENCY`), так что 30 серверов обходятся примерно за
полторы минуты — с запасом укладывается в пятиминутный интервал.

Если серверов станет много и обход начнёт не успевать, есть три ручки:
уменьшить `MONITOR_RU_POINTS`, поднять `GEOPINGER_CONCURRENCY` (но не выше
`GEOPINGER_MAX_CONCURRENCY` на самом пингере) или увеличить
`MONITOR_INTERVAL_SEC`. Пропущенный обход не ломает логику: цикл видит, что
предыдущий ещё идёт, и не запускает второй параллельно.

## Состояние

Открытые инциденты, счётчики за сутки и отметка об отправленной сводке
лежат в `bot/monitor_state.json`. Благодаря этому перезапуск бота не рождает
повторных алертов по уже известным авариям и не теряет длительность простоя.
Файл в `.gitignore` — он у каждого развёртывания свой.

## Тесты

```bash
python3 bot/tests/test_monitor_logic.py   # правила вердиктов, разбор данных
python3 bot/tests/test_monitor_flow.py    # цикл целиком на подставном пингере
```

Оба запускаются без сети и без токена бота. `test_monitor_flow.py` проходит
девять сценариев: блокировка, падение узла, деградация, молчащий пингер,
массовый сбой, тихий режим, удаление сервера из панели, недоступный основной
API — и проверяет, что уходит ровно столько сообщений, сколько должно.
